Pulse Analytics Dashboard

An analytics interface built to showcase interaction detail on its own terms, with no backend behind it and none claimed.

pulse-analytics-dashboard.obiomachibuezej.workers.dev

What this project is honestly for

Pulse Analytics Dashboard has no real backend, and this case study will not pretend otherwise. It exists to demonstrate interaction level polish on a dashboard style interface, the kind of detail that is easy to describe and genuinely hard to get right in practice.

The detail that mattered most

The hero mockup leans back and shrinks slightly as the page scrolls, while also tilting subtly in response to the cursor. Those are two separate transform layers, tracked independently, verified not to fight each other or produce a visual stutter when both are active at once. Getting that combination smooth, rather than picking one effect and dropping the other, was the actual engineering problem here.

Elsewhere in the interface

Chart tooltips are custom built rather than relying on a browser's default tooltip rendering, which is what allows them to match the rest of the interface's visual language. Every data table on the site reveals its rows in a cascading sequence rather than appearing all at once, and buttons carry a magnetic pull toward the cursor as it approaches.

What I would change today: without a real backend, every number on the dashboard is static. The interaction design holds up, but I would not want anyone mistaking this for a working analytics product, and the case study says so plainly for that reason.

WHY BUILD A DASHBOARD WITH NO REAL DATA BEHIND IT
Requirement: practice the interaction details that separate a good dashboard from a mediocre one, independent of any real data source → Constraint: wiring up a real backend would have taken time away from the actual thing being practiced, the interaction design itself → Decision: static data, full focus on scroll behavior, tooltips, and transitions → Consequence: a convincing interface with nothing real underneath it, which is fine as long as it is labeled honestly, which is why this case study does that directly

This project answers a narrower question than most others here: not "can this run a real business," but "can I make an interface feel like production software." It answers that question well and no other.
