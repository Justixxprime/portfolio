A 21 page site for a real African food export company, built to search engines' real specifications rather than guessed at.

LAGOS, NIGERIA → EXPORTED WORLDWIDE → EST. 2013
justixxprime.github.io/shelemj-website

The client

ShelemJ Resources Limited exports African food products. The site was built as a plain HTML project, styled with Tailwind through its CLI build rather than a framework, across 21 pages.

Real structured data, not guesswork

Every one of the 21 pages carries JSON LD structured data, Organization and FAQPage schema, added after correcting a prior audit that had gotten the details wrong. This is what lets a business's own facts, its name, its FAQ answers, surface directly inside Google search results rather than staying invisible to it.

The logo decision

An early draft of the site had a Trusted By section with client logos meant to signal credibility. Those logo files did not actually exist. Rather than leave a placeholder or invent something that looked plausible, that section was replaced with badges the business could genuinely verify: CAC registration, NEPC registration, and its established year. It is a smaller, less flashy claim, but every part of it is true.

A bug solved twice

The same backdrop filter issue that broke Amani Community Trust's mobile menu also showed up here, and was fixed the same way, by understanding the actual mechanism rather than trying different CSS until something happened to work.

What I would change today: the FAQ content was written before the structured data was added. If I rebuilt this now, I would write the FAQ answers with the schema in mind from the start, since a couple of them are longer than what displays well in a search result snippet.

WHY TAILWIND CLI, NOT A FRAMEWORK
Requirement: 21 pages of mostly static content, product listings, and a blog, with no interactive application logic → Constraint: a React or Vite setup adds a build step and complexity that this content does not need → Decision: plain HTML compiled with the Tailwind CLI, no JavaScript framework at all → Consequence: simpler deployment and a smaller page weight, at the cost of manually repeating shared markup like the header and footer across every page

A framework would have made shared components easier to manage across 21 pages. For a site with no client side application logic, that convenience did not outweigh the added build complexity for a solo developer to maintain.
