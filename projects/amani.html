Amani Community Trust

A portfolio concept, not a real client relationship, built to show what a fully animated, installable nonprofit site can look like.

justixxprime.github.io/amani-community-trust

An honest starting point

Amani Community Trust does not correspond to a real nonprofit organization. It uses placeholder photography rather than real client photos, and exists as a self directed concept project rather than commissioned client work. That distinction matters and belongs here plainly rather than implied otherwise.

What it demonstrates now

Redesigned since the first version, with a fuller information architecture: a hero that states the organization's registered status and founding year plainly, quick links into Education, Health Outreach, Economic Empowerment, and an Impact section, and a trust strip showing the partner organizations it works alongside, from grassroots cooperatives to regional clinics and county health boards. A four step donation flow with progress tracking, a nine article field journal, and volunteer sign up round out the site. Still fully animated and installable as a progressive web app.

A bug worth mentioning once

The mobile menu originally broke in a way that looked unrelated to its actual cause. A backdrop filter applied to the header was quietly changing how a fixed position child element inside it behaved, which is a real, specific CSS interaction rather than a vague rendering glitch. The same root cause turned up again later on the ShelemJ project, and being able to recognize it immediately the second time is a better sign of understanding than fixing it once by trial and error.

What I would change today: the placeholder photography is honest about being a concept project, but it is also the first thing anyone notices. If this ever became real client work, sourcing real photography would be the first priority, ahead of any further feature work.

WHY PLAIN HTML, NOT A FRAMEWORK
Requirement: 22 pages, fully animated, installable as a PWA, with no ongoing hosting cost → Constraint: this is a self directed concept, not a funded client project, so build complexity had to stay low → Decision: plain HTML5, CSS3, and JavaScript, deployed on GitHub Pages for free → Consequence: no component reuse across pages the way React would give, traded for zero build step and zero hosting bill

A framework would have made the 22 pages faster to maintain as a set. It would also have added a build step and a dependency chain for a project with no budget behind it. Plain HTML was the honest choice here.
